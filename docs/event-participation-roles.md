# Event participation roles

The event detail page presents six role cards, each linking directly to its registration form. The registration page shows event name, date, location and deadline, then a role summary with a change action and the relevant form. Roles are ordinary participant (`ATTENDEE`), athlete (`ATHLETE`), referee (`REFEREE`), team leader (`TEAM_LEADER`), coach (`COACH`) or medical staff (`MEDICAL_STAFF`). The standalone role picker uses descriptive cards instead of a dropdown. Existing links with `mode=individual` or `mode=group` continue to open the original athlete registration UI and flow. Signed-in athletes with a linked athlete profile can use that profile for direct registration or switch to the full individual/team form. Both light and dark layouts adapt to mobile screens.

Non-athlete applications use `EventParticipation`, independently of athlete competition registrations and account type selections. Guests enter contact details; signed-in applicants use their account name/email. A team leader selects the federation for this event, using the event's participating federation list when configured. Applications begin as `SUBMITTED`, with a unique reference code. One email can register multiple roles, but cannot submit the same role twice at the same event. Selecting a role does not grant CMS or scoring access.

Applicants can view their linked applications at `/account`. CMS users view, filter and review these applications at `/cms/registrations`. Review records the status, reason, timestamp and reviewer. The existing athlete registration, identity, disciplines, payment and ticket flow stays in `AthleteEventRegistration`.

All roles receive an A6 PDF ticket with their role and QR code once confirmed. Applicants (including guests) and CMS users open `/tickets/<referenceCode>` and download through the shared `/participant-auth/tickets/<referenceCode>/pdf` endpoint. Public ticket data excludes email and phone. Confirmation atomically enqueues an email with the PDF attachment through the existing SMTP settings, retry queue and background worker. Repeated confirmation does not enqueue another email; revoked applications cannot download official tickets and queued emails are skipped. Migration `20261010130000_participation_ticket_email` queues tickets for previously confirmed role applications. Non-athlete applications have no competition fee; athlete payment rules are unchanged.

Apply migration `20261010110000_event_participation_roles` before running the updated backend. Verification: build both apps, run frontend lint, and run `tests/integration/event-participation-live.cjs` inside the local backend container. It creates and removes isolated fixtures to test registration roles, federation validation, privacy, review permissions and event registration windows.
